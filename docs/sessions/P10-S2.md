## The Evaluation

§43 words this session as a CONDITIONAL: "Introduce dedicated search infrastructure **if justified**." The P10-S1 measurement harness provides the evidence this session evaluates.

### The decision

**Do NOT introduce dedicated search infrastructure (e.g., a managed search service) now.** The PostgreSQL FTS + pg_trgm engine (`postgres-fts-v1`) serves the corpus at interactive latency with zero additional infrastructure, and every §29 trigger is unmet by one or more orders of magnitude.

### The standing protections (why this decision is safe to hold)

1. **The §17 vendor-neutral boundary is already structural**: the `SearchDocument` store is the abstraction — a vendor engine would replace `engine.ts` + `indexing-service.ts` behind the same store and the same `publicSearch` contract; no domain module imports an engine (§28 direction rule). The domain model does not depend on the engine — verified by the module barrels.
2. **The re-evaluation triggers are explicit and measurable** (re-run `bun /home/z/e2e/perf-baseline.ts`): search median latency > ~2s over a colocated DB; corpus > ~50k documents; sustained query load where the engine's share of DB capacity measurably competes with the OLTP workload.
3. **The honest cost of waiting is near zero**: the migration surface is two files in the search module; the seed/E2E suites already assert engine-agnostic contracts (`engine postgres-fts-v1` is a label, not a dependency).
