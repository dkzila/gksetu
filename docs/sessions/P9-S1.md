## What Was Delivered

### 1. The §6 Translation Entity (prisma/schema.prisma)

- `Translation` — the provenance LINK between two representations of the same canonical anchor: `sourceContentType`/`sourceContentId` + `targetContentType`/`targetContentId` (polymorphic, the EditorialTask pattern), `languageId` (§6 "language" — the TARGET language), `sourceRevisionNumber` (the sync point), `status` (DRAFT → PUBLISHED → OUTDATED on drift → RETIRED), `aiAssisted` (§26), `notes`, `createdById`.
- **Architecture adaptation (deliberate, §35):** the §6 row's "translated fields" live in the TARGET representation — a full first-class ContentItem/QnA riding the §19 workflow with immutable §36 revisions (the P2-S2 foundation). The Translation row records the relationship; business identity is never duplicated.
- Uniqueness is service-enforced (the event-anchored ContentItem precedent): one ACTIVE link per (source, language) — §7/§11 no-duplication — and one per target; RETIRED rows never block a fresh pairing, history stays auditable.

### 2. The Translations Module (`src/modules/translations/`)

- **`service.ts`** — `listTranslations` (§38-scoped by the anchor's country, GLOBAL anchors = the ADMIN platform workspace; derived drift: source live revision vs the sync point, never a guess), `createTranslation` (source must be PUBLISHED; target language ACTIVE + configured on the anchor's market — §35, GLOBAL anchors check the default market; DRAFT target created in the same transaction with the working copy SEEDED from the source's live revision — translate in place, the CAT-tool convention; P2002 → the honest 409), `retireTranslation` (§36 soft delete of the link — both content rows stand), `onRepresentationPublished` (the publish-transaction hook: drift flip + target sync, both system-audited), `findActiveTargetLink` (the §19 gate lookup), `getStaleTranslationsForItems` (the §35 render join), `translationInsightMetrics` (§32).
- **`ai-translate.ts`** — the §26 model prompt: faithful translation, fact preservation hard rules, standard target-language legal terminology, and structure preservation for every §23 shape (TIMELINE "date — event" lines, PROFILE "key: value", COMPARISON pipe rows); JSON-only output, fence-tolerant parsing.
- **`ai-service.ts`** — `generateAiDraft`, **server-only by construction**: imported exclusively by its API route, never re-exported through the module barrel. The z-ai SDK stays one hop beyond every client-reachable import chain (a load-bearing boundary — see "Verification-Found Fixes").

### 3. Workflow Wiring (§19 step 5 + §36 hooks)

- `content-service` + `qna-service` publish transactions call `onRepresentationPublished` — drift (a source's newer revision flips its synced translations OUTDATED) and sync (a target's publish re-syncs to the source's CURRENT live revision) ride the same atomic transaction as the publish.
- `wireContentWorkflow`/`wireQnaWorkflow` open a **LOCALISATION_REVIEW** task (HIGH priority, one per cycle, double-submit guarded) on `submit_review` when the item carries an active translation link — the §19 step-5 gate in the same cycle as the editorial review.

### 4. §35 Public Honesty (render-service + reader UI)

- The knowledge page's `translations[]` gains `stale` + `sourceLanguageCode` (derived from the link's sync point vs the source's live revision). The reader switcher shows the orange "updated since" hint on drifted translations — §36 is an editorial freshness flag, never a visibility flag. hreflang unchanged: a published translation is a published page.

### 5. API (§37)

| Endpoint | Method | Auth | Purpose |
|---|---|---|---|
| `/api/translations` | GET | `translations:manage` | The §18 workspace list + §32-shaped stats (tracked vs in-fact pairs) |

## Verification-Found Fixes (2 — both found by the live smoke, both structural)

1. **The z-ai SDK leaked into the client bundle**: `feedback-section (client) → content-quality → analytics barrel → insights-analytics-service → translations barrel → service.ts → ai-translate → z-ai-web-dev-sdk` — module-not-found 500s on every page. 2. **The ADMIN grant landed in the wrong block** (a `MultiEdit` match on the shared `feedback:manage` list ending): ADMIN 403'd on its own workspace. Fixed.
