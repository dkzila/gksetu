# P5-S2 — Saves and Collections

**Master Plan §43, Phase 5 Session 2** · "Implement saves and collections."
*(Builds on the P5-S1 follow half of the same module, the P2 knowledge/content canonical stack that saves point at, and the P4 discovery surfaces where the save affordance now lives.)*

## Goal

The **`SavedItem`** and **`Collection`** models and their versioned APIs are live — save/unsave/move/list/state plus collection create/rename/delete for **KNOWLEDGE_UNIT** and **CONTENT_ITEM** objects with the **§10 semantics** (retrieval, never a recommendation signal; default "Saved" collection; stable canonical references; honest tombstones for withdrawn content) — plus the product surfaces: the **Save button** on every knowledge page, the **`#/saved`** management view (§31 control surface) and the console's save/collection API verification card.

## Inputs

- §6 (`SavedItem`: user_id, object_type, object_id, collection_id, saved_at; `Collection`: id, user_id, name, visibility), §7 (one canonical record, many representations — the save's stable-reference target), §10 (**Save is an explicit retrieval/bookmark action — never a recommendation or personalisation signal**; default collection "Saved"; custom collections user-defined; stable references so updates never duplicate; tombstones for deleted/withdrawn content), §15.3 (public content browsable across countries — the basis for saves carrying **no §14 country guard**), §16 (canonical paths in summaries), §31 (account controls over saved data), §36 (honest object statuses), §37 (client-agnostic, idempotent, typed errors), §39 (the same Bearer-token APIs a mobile app calls).
- Reused platform precedents: the P5-S1 follow-half patterns (typed-error service, idempotent mutations, truthful state endpoint, `#/following` private-view + console-card pair), the country-locale `buildCanonicalUrl`/`resolveLocaleContext` (§16/§35), `recordAudit` (P1-S5), and the knowledge module's public identity conventions (unit slug-or-id; content-item representation id — the same id every public knowledge page already exposes).

## Tasks

1. **Prisma** (additive, `db:push`ed to Supabase — no data loss): `SavedObjectType { KNOWLEDGE_UNIT, CONTENT_ITEM }` (QnA/Question/MockTest join in P7, CurrentEvent in P6 — the P5-S1 `FollowObjectType` additive precedent; **EXAM/TOPIC are deliberately absent** — §10 assigns those to follows), `CollectionVisibility { PRIVATE }` (PUBLIC joins with the P8 sharing system), the `Collection` model (unique `[userId, name]`, `isDefault` bootstrap flag, cascade with the user) and the `SavedItem` model (unique `[userId, objectType, objectId]` — one row per object per user, so re-organising is a **move**, never a copy; per-user/per-collection/per-object indexes; cascade with user and collection).
2. **Audit vocabulary**: `user.save.create` / `user.save.remove` / `user.save.move` + `user.collection.create` / `user.collection.update` / `user.collection.remove` actions and `SavedItem` / `Collection` object types — every mutation audited with the object label (`KNOWLEDGE_UNIT:slug` / `CONTENT_ITEM:{unitSlug}#{format}`) and before/after collection context (§19 precedent).
3. **The save half** (`src/modules/follow-save/save-{types,validation,service}.ts`):
   - `saveObject` — resolves the object (unit via slug-or-id row read, content item via the public representation id), enforces **eligibility** (VERIFIED/OUTDATED units and PUBLISHED items only — `UNIT_NOT_SAVABLE`/`CONTENT_ITEM_NOT_SAVABLE` 409 with honest §36 explanations: DRAFT "not public yet", ARCHIVED/RETIRED "tombstone" language, SCHEDULED "goes live automatically (§19)"), resolves the target collection (explicit `collectionId` scoped to the caller, else the **default-collection bootstrap** — first save lazily creates "Saved", P2002 race → re-fetch), a 500-save sanity cap (§30), **idempotency** (existing row → 200 + `alreadySaved`, keeping its current collection — re-organising is never a side effect of saving), then creates + audits.
   - `unsaveById` — scoped `findFirst({ id, userId })`, summary captured before delete, audited.
   - `moveSavedItem` — scoped row + owned target collection; same-collection move is an idempotent no-op; otherwise `collectionId` update + `user.save.move` audit (before/after collection names).
   - `listMySaves` — batched unit+item loads, all collections with live counts (default first, name-ordered), §16 canonical paths per object's own market context (COUNTRY-scoped units in their own market; GLOBAL units in the requesting market; content items in their unit's market in the **item's language**), live-revision titles for items, honest statuses, `savedAt desc`, coherent counts.
   - `getSaveState` — truthful **without** the eligibility guard (the P5-S1 key decision): it answers "have I saved this?" even for retired/scheduled objects; rejection surfaces on the save attempt.
   - `createCollection` / `renameCollection` / `deleteCollection` — 20-collection cap, `COLLECTION_NAME_TAKEN` on duplicates, `DEFAULT_COLLECTION_IMMUTABLE` 409 protecting the §10 bootstrap from rename/delete, and **§31-safe deletes**: deleting a non-empty collection moves its items back to the default (response reports `movedItems`) — a bucket is deleted, never the saves in it.
4. **Validation** (`save-validation.ts`): the §10 boundary is **structural** — `objectType: EXAM`/`TOPIC` rejects at validation with an explicit redirect to `POST /api/follows`; QNA etc. reject as P7 vocabulary; `CONTENT_ITEM` refs are id-only (content items have no slug — §7 identity is unit × language × format); collection names 1–60 chars.

## API

| Endpoint | Contract |
|---|---|
| `GET /api/saves?type=&collection=&country=&language=` | `{ items: PublicSave[], counts: { total, KNOWLEDGE_UNIT, CONTENT_ITEM }, collections: PublicCollection[] }` — the caller's saves with resolved summaries (§16 paths, live-revision titles, §36 statuses) + all collections with live counts. |
| `POST /api/saves` | Body `{ objectType: 'KNOWLEDGE_UNIT'\|'CONTENT_ITEM', objectRef, collectionId? }` → **201** `{ save, alreadySaved: false }` or **200** `{ save, alreadySaved: true }` (idempotent). Typed 404/409 rejections (§36 eligibility, §30 caps, §10 boundary at validation). |
| `DELETE /api/saves/{id}` | **200** `{ removed: true, save }` — scoped to the caller; **404** `SAVE_NOT_FOUND` otherwise. |
| `PATCH /api/saves/{id}` | Body `{ collectionId }` → **200** `{ save }` — move between collections (idempotent when already there). |
| `GET /api/saves/state?objectType=&objectRef=` | `{ saved, save, objectFound, objectSlug }` — truthful per object, no eligibility guard by design (the P5-S1 decision). |
| `POST /api/collections` | Body `{ name }` → **201** `{ collection }` (20 per user; `COLLECTION_NAME_TAKEN` 409). |
| `PATCH /api/collections/{id}` | Body `{ name }` → **200** `{ collection }` (custom collections only — `DEFAULT_COLLECTION_IMMUTABLE` 409). |
| `DELETE /api/collections/{id}` | **200** `{ removed: true, movedItems, name }` — items fall back to the default collection (§31); default itself undeletable. |

All eight require `Authorization: Bearer` (401 otherwise — §30/§31 private per-user data).

## Acceptance

- §10: saves are **retrieval bookmarks, structurally separate from follows** — the enum, the validation redirect (EXAM/TOPIC → `/api/follows`), the module docs, the `#/saved` footnote and the console copy all carry the boundary; nothing in this session ever treats a save as a recommendation input or a follow as a retrieval object.
- §10 stable references: saved rows store canonical ids (never slugs); the unit-level Save button survives representation updates (a new ContentRevision re-resolves under the same row — verified by the tombstone fixture's live-revision title).
- §10/§36 tombstones: RETIRED/ARCHIVED objects never delete the row — the list resolves them honestly (status, title, format, path) with tombstone notes in the UI.
- §31: saves are reviewable (`#/saved`), reversible (one-click remove everywhere), movable between collections, and **deleting a collection can never destroy saves** (items fall back to the default; the response and toast report how many moved).
- §37/§39: eight idempotent-where-meaningful, typed-error, envelope-conformant endpoints — a mobile client can implement the entire save/collection feature against them without the website.

## Key Decisions

1. **Saves carry no §14 country guard** (the deliberate contrast with P5-S1): follows are personalisation signals, so exams/country-scoped topics are followable only from the home market; saves are **retrieval of public content**, and §15.3 explicitly allows browsing any market's public content — so any reader (including countryless accounts) can save any market's public objects. Verified end-to-end with the countryless reader + the IN COUNTRY-scoped unit.
2. **One row per (user, object)** — the unique `[userId, objectType, objectId]` makes the state endpoint truthful ("have I saved this?") and re-organising a **move** (§10's "no duplicates" guaranteed at the storage layer). Idempotent save returns the existing row in its current collection, never a silent move.
3. **The unit-level Save button** saves the KNOWLEDGE_UNIT — the canonical record — rather than any single representation: the §16 knowledge-page URL identifies the unit, and the §10 stable-reference rule is strongest there (language additions and new revisions never duplicate the row). CONTENT_ITEM saves exist in the vocabulary (§10 lists both) and are exercised live in the console via the representation id the public page already exposes.
4. **Eligibility = publicly-live today**: VERIFIED/OUTDATED units and PUBLISHED items are savable; ARCHIVED/RETIRED are not (existing saves tombstone); SCHEDULED is not (it goes live automatically, §19). The **state endpoint still reports saved=true** for ineligible objects — honesty over convenience, the P5-S1 precedent.
5. **Deleting a collection falls back to the default** rather than cascading or refusing: a bucket is organisation, not data (§31 reversibility); the default "Saved" itself is immutable (name + existence) because §10 fixes it as the bootstrap anchor.
6. **§16 path correction shared with the follow half**: both halves' market resolution had inherited a subtle bug — the path's omitted-language reference came from the *resolved* language instead of the *country's default*, so `?language=hi` produced `/gk/…` paths instead of `/hi/gk/…`. Fixed in `marketFromResolution` (save half) and `resolveTopicMarket`/`toTopicSummary` (follow half — GLOBAL topics now path in the reader's resolved language; COUNTRY topics keep their own market's default, the canonical form where the path must be reachable). The P5-S1 documented assertions (labels, default-market paths) are unchanged — verified by the regression suite.
7. **Mobile truncate fix (both management views)**: a `truncate` span inside an inline-block button cannot shrink (whitespace-nowrap makes the intrinsic min-width the full text), so long saved titles overflowed at 390px. The card pattern now uses a block `w-full` button inside a `basis-52` title column, letting the actions wrap to their own line. Applied to `#/saved` and preventively to the `#/following` cards (the same latent pattern).
