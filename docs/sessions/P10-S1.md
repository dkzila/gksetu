## Goal

Measure the platform's real performance profile (the honest §29 prerequisite) and optimise what the measurements justify — no speculative infrastructure, no premature distribution (§46.12).

## What Was Delivered

### 1. The measurement harness (`/home/z/e2e/perf-baseline.ts`)

17 probes over live HTTP — the public reader surfaces (homepages, knowledge pages, search, sitemap, feed, exams) + the ops surfaces (insights, product analytics, market-ops ×3, workspaces, editorial) — each timed 3× after a warmup pass (route compile + cold caches excluded), medians reported. Reusable as the regression harness (`bun /home/z/e2e/perf-baseline.ts [label]`).

### 2. The measured baseline (Supabase session pooler, ap-south-1 — the real network shape)

The fundamental constant: **~240–400ms per DB round-trip** (health's 3 queries ≈ 722ms). The baseline medians: insights **17,458ms** · market-ops IN overview 9,286ms · FR overview 8,419ms · IN knowledge page 6,535ms · market-ops summaries 4,250ms · sitemap index 3,593ms · IN sitemap segment 3,459ms · IN homepage 2,587ms. **Sum of medians: 68,858ms.**

### 3. The optimisations (each §29-justified by a measurement)

1. **The shared 60s census cache** (`loadSitemapInventoryCached` — globalThis + epoch-guarded single-flight, the P9-S2 snapshot pattern): the census walk (~14 queries ≈ 3.5s) feeds /sitemap.xml, both sitemap segment paths, /api/seo/status and both market-ops routes — repeated expensive reads, exactly §29's cache trigger. The **observation import guard keeps the UNCACHED read** (a census guard must see the freshest truth). Sitemap index **3,593 → 7ms** · segment **3,459 → 4ms** · market-ops summaries **4,250 → 769ms**.
2. **The insights parallelization**: the three §32 families, the editorial family's three metric helpers, and the queryCoverage engine re-runs (7 sequential ~1s engine calls) — all independent reads, all `Promise.all`. Insights **17,458 → ~3,850ms (-78%)**.
3. **The census loader's per-language batch + the hreflang parallelization**: the per-language unit/event queries (2×languages sequential round-trips) batched into one `Promise.all`; the market-ops hreflang derivation (67 sequential snapshot resolutions for IN) parallelized. Market-ops overviews **9,286 → ~4,000ms**.

**Sum of medians: 68,858 → ~39,000ms.** The unchanged tail (recorded honestly, not optimised — §29 discipline): knowledge pages ~4–10s (the render service's sequential composition chain), homepages ~1.5–2.5s, product analytics ~3.5s — the next measured targets if load ever justifies deeper batching.

### 4. Regression-proof

Both prior suites re-run green against the optimised code: **P9-S4 55/55** (expectations updated to the P9-S5 baseline with supersession notes — FR live with 9 census URLs, GB 8/3 after the phantom-URL fix, footprint 84) + **P9-S5 34/34**. The sitemap XML smoke-verified through the browser (19 segments, FR present, the cache serving the true census).

## Known Issues / Honest Gaps

- The census cache serves reads up to 60s stale (the locale-snapshot precedent) — a fresh publish takes up to a minute to reach /sitemap.xml and the market-ops views; the launch path and the import guard read fresh.
- The knowledge-page render chain and the homepage compositions remain the slowest surfaces (measured, recorded, deliberately not restructured this session — the fix would be deeper query batching in the render service; §29: wait for the load that justifies it).
- Run-to-run variance over the Mumbai pooler is significant (the IN knowledge page swung 6.2–10s across runs) — the medians are honest but the sandbox↔Mumbai RTT dominates everything; a production deployment colocated with the DB would shift the whole profile.
- The login rate limiter (10/15min) was hit twice during the measurement loop (the harness logs in once but the E2E suites stack on top) — cleared by the documented daemon restart both times.

## Handoff (for P10-S2 — dedicated search infrastructure if justified)

- The search surface measured at **~1.0–1.9s median** for a constitution query (the FTS + pg_trgm engine over the pooler) — fast for the corpus size (49 documents).
- §29's trigger is "large corpus/latency requirements" — neither is met (49 documents; ~1s latency). The honest P10-S2 evaluation is expected to be **NOT justified** — the decision should be documented against these measurements, with the §17 vendor-neutral boundary (the domain model does not depend on the engine) stated as the standing protection.
- The perf harness is the standing measurement tool for the re-evaluation when the corpus grows.
