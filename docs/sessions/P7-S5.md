## Goal

**One §11 engine, two applications, zero duplication.** The quick mock ("Quick mock" at `#/quick-mock`) lets a signed-in learner generate a timed test scoped to the union across their goal ∪ followed exams (COMBINED) or exactly one of them (EXAM — §11's single-exam mode): the scope resolves through `getCombinedExamView` (the same call the dashboard's learning queue uses — never a second union implementation), the published, language-matched question pool is deduplicated strictly by canonical unit (§11 step 6 — one question per unit, deterministic pick: difficulty ascending → freshest → id), and the composition walks the combined queue's own §11 order. The attempt freezes the deal at start (§6/§36): `generatedScopeJson` (mode, covering exams, unit/question counts) with `mockTestId` null — a widening of the §6 row, editorial attempts untouched. Deadline (`max(5, ceil(1.5/question))` minutes) and pass mark (40%) are stated rules rendered verbatim (§9 transparency); the submit path is UNCHANGED — the conditional claim, server-side scoring, immutable answers[] and the §22 mastery fold all apply to generated attempts exactly as to editorial ones. `POST /api/mock-tests/quick` while a sprint is live resumes it (§22: finish the live one first). The dashboard queue gains scope chips (All my exams / each eligible exam — `?exam=` on `GET /api/dashboard`, one exam in the engine's input set), the revision-queue lists follow the chosen scope while the mastery stats stay overall (honest), and the exam page's mock-test list gains a "Quick mock for this exam" card deep-linked to the preselected scope (`#/quick-mock/{exam}/`).

## Key Decisions

1. **A generated attempt, not a stored test** (§11/§22): the combined view is COMPUTED — never a separately stored syllabus/content row. The quick mock anchors on a SCOPE SNAPSHOT (`generatedScopeJson`, mockTestId null) — the §6 attempt itself is honest stored user state; no editorial MockTest row is polluted, no workflow states abused.
2. **The same engine, three ways** (§11): the dashboard queue (combined), the dashboard queue (`?exam=` — single-exam mode) and the quick-mock generator all call `getCombinedExamView` — one union implementation, one dedup, one ranking; §22's "applied identically" is literal.
3. **One question per canonical unit** (§11 step 6): the pool deduplicates strictly by canonical identity (never title similarity), picks deterministically per unit (BASIC → ADVANCED, then freshest, then id) and walks the queue's own §11 order — the same topic can never appear twice in one mock.
4. **The runner is one UX** (§22): `TestRunnerView` generalized rather than duplicated — the generated scope IS the test's identity (title/breadcrumb/badges); deadlines, scoring, the result review and the §22 mastery fold are byte-for-byte the editorial path (only the audit labels and projections know the anchor differs).
5. **Scope resolved caller-side** (§28): `resolveQuickMockScope` lives in personalisation (it owns the §9 signals + §35 market plumbing), hands the set to the assessment service — the mastery-market pattern; the import direction stays personalisation → assessment, never the reverse.
6. **Honest sizing everywhere** (§36/§9): pool sizes on every card, empty pools disabled with reasons, a short pool serves shorter with a note, the duration/pass rules stated verbatim on the surface and mirrored in the API, and the resume rule says exactly what it does.
