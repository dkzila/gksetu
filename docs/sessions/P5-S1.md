# P5-S1 — Follows

**Master Plan §43, Phase 5 Session 1** · "Implement follows."
*(Builds on the P1-S2 token identity layer, the P3 exam/taxonomy layers and the P4 discovery surfaces where the follow affordances now live.)*

## Goal

The **`UserFollow`** model and its versioned APIs are live — follow/unfollow/list/state for **EXAM** and **TOPIC** objects with server-enforced **§14 country scoping**, **§16 canonical summaries**, audited mutations and idempotent semantics — plus the product surfaces: the **Follow button** on exam/syllabus/topic pages, the **`#/following`** management view (§31 control surface) and the console's follow API verification card.

## Data

- **Schema**: `UserFollow` + `FollowObjectType` (additive; pushed with `db:push`, no seed change — follows are user-generated data, never seeded).

## API

| Endpoint | Contract |
|---|---|
| `GET /api/follows?type=&country=&language=` | `{ items: PublicFollow[], counts: { total, EXAM, TOPIC } }` — the caller's follows with resolved summaries (§16 paths, §35 labels, §36 statuses). |
| `POST /api/follows` | Body `{ objectType: 'EXAM'\|'TOPIC', objectRef }` → **201** `{ follow, alreadyFollowing: false }` or **200** `{ follow, alreadyFollowing: true }` (idempotent). Typed 403/404/409 rejections (§14/§36/§30). |
| `DELETE /api/follows/{id}` | **200** `{ removed: true, follow }` — scoped to the caller; **404** `FOLLOW_NOT_FOUND` otherwise. |
| `GET /api/follows/state?objectType=&objectRef=` | `{ following, follow, objectFound, objectSlug }` — truthful per object, no §14 guard by design. |

All four require `Authorization: Bearer` (401 otherwise — §30/§31 private per-user data).

## Acceptance

- §10: follow is a personalisation signal, structurally separate from saves — the module's headers, DTOs and the `#/following` footnote all carry the boundary; the save half (SavedItem + Collection) has a reserved home (P5-S2) and **never** treats follows as retrieval objects or saves as recommendation signals.
- §14 is enforced **server-side in the service** (never by UI hiding): exams and COUNTRY-scoped topics only follow from the user's home market; GLOBAL topics are open to every market; cross-country following remains an explicit future product decision, not a default.
- §9/§31: follows are explicit, reversible (one-click unfollow everywhere), reviewable (`#/following`) and auditable (`user.follow.*`).
- §37/§39: the four endpoints are versioned, idempotent where meaningful, typed-error and envelope-conformant — a mobile client can implement the entire follow feature against them without the website.

## Key Decisions

1. **The state endpoint does not enforce §14** — it answers "am I following this?" truthfully for any object (even cross-market or retired); the guard lives on the follow **attempt**. This keeps button state honest and lets the UI surface the server's explanation instead of hiding the affordance.
2. **`objectRef` is the platform ref convention** (slug-or-cuid, `findExam` semantics) — the same identity grammar as every public endpoint; follow rows store the **canonical id**, never a slug (renames can't break follows; §36 soft-delete means rows never dangle).
3. **Summaries are resolved in the object's own market** (a GB exam lists `/uk/exams/…`) using the same `buildCanonicalUrl` as the public compositions — one §16 truth; the `#/following` cards navigate there via market-aware callbacks, never by re-deriving URLs client-side.
4. **Follows are role-agnostic** — any ACTIVE user (READER…ADMIN) can follow; roles gate editorial power, not personal features (§20 separation).
5. **The 100-follow cap** is a §30 abuse posture, generous for real learners; typed `FOLLOW_LIMIT_REACHED` 409.
6. **No follow seed data** — follows are user-generated by definition; the console card exercises the real APIs with the seeded demo objects instead.
7. **The app-shell `initialize()` fix** (auth bootstrap on every load) is a P1-S2 gap that P5-S1 surfaces made visible — fixed in the shell, not in the follow components, so every personalised surface (P5-S2…S5) inherits it.

## Handoff (for P5-S2: saves and collections)

- The follow half is feature-complete for today's object vocabulary: `UserFollow` + 4 endpoints + UI affordances + console card. P6's ENTITY/THEME follow types extend `FollowObjectType` additively (enum + `resolveFollowable` branch + validation vocabulary) — no migration risk.
- The save half joins this module: `SavedItem` (user, objectType, objectId, **collection**) + `Collection` (user, name, visibility; default "Saved") per §10 — tombstone handling for RETIRED objects should reuse the §36 status notes pattern from `#/following`, and the default-collection bootstrap belongs in the service (first save creates it).

- The §11 combined-queue consumption of followed exams (list → active versions → union) lands with the P5-S4 personalised dashboard; `listMyFollows(type: 'EXAM')` already returns everything it needs (slugs + statuses to resolve active versions).
