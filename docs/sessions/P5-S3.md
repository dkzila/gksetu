## Goal

The **`UserGoal`** model and the **onboarding state machine** are live — one declared goal per user (exams + subjects + level + study language + target year + daily pace, **full replacement** semantics per §9), a four-step guided flow at **`#/onboarding`**, the ongoing **`#/profile`** management surface (§31 — review, change, remove), self-service profile basics via `PATCH /api/profile` (name / home country / preferred language with the §35 rules), and the console verification card. Goals are **explicit §9 signals only** — they drive personalisation, never proof the user will sit an exam; they are changeable and removable at any time (§31).

## API

| Endpoint | Contract |
|---|---|
| `GET /api/goal?country=&language=` | `{ goal: PublicGoal \| null }` — hydrated with §16 paths and §35 labels in the resolved market (explicit query → declared study language → preferred language → home default). |
| `PUT /api/goal` | Body `{ exams[], topics[], level?, studyLanguageCode?, targetYear?, dailyMinutes? }` → **201** `{ goal, created: true }` / **200** `{ goal, created: false }` — **full replacement** (§9). Typed 404/403/409/400 guards (§14 market, §36 status, §35 language, §30 caps: ≤10 exams, ≤25 subjects). |
| `DELETE /api/goal` | **200** `{ removed: true }` — join rows cascade (§31 reversible). **404** `GOAL_NOT_FOUND` when absent. |
| `POST /api/onboarding` | Body `{ action: 'complete' \| 'skip' }` → `{ user }` — idempotent state machine (§6); COMPLETED never downgrades. |
| `GET /api/profile` | `{ user, goal }` — the caller's user (incl. onboarding state) + resolved goal. |
| `PATCH /api/profile` | Body (all optional, explicit null clears) `{ name?, homeCountryIso?, preferredLanguageCode? }` → `{ user }` — §35 rules enforced server-side, identical to registration; §14 goal guards re-apply at their own mutation time. |

## Key Decisions

1. **One goal per user, full replacement** (§9 "change goals at any time"): `PUT /api/goal` carries the complete goal state; join rows are rebuilt in one transaction, never merged — a goal is one coherent declaration, not a patchwork of events.
2. **The onboarding state machine is owned by the personalisation module**, not identity-access (§28 boundary): identity owns the identity/auth fields of `User`; this module owns `onboardingStatus` and the `UserGoal` aggregate. Exam/topic summaries read canonical rows directly — read-only projections, no reverse dependency.
3. **§14 guards at declaration time, honest reads forever**: a goal exam must be ACTIVE + home-market when declared; if the market context later changes (country activation, exam retirement), existing rows resolve honestly in the read (§36) and future edits follow the new market — the P5-S1 follow precedent.
4. **`setMyGoal` transaction timeout raised to 20s** (fix found by this session's verification): the 7-statement interactive transaction overflowed Prisma's 5s default on the first cold pooled Supabase connection ("Transaction already closed" → 500). Atomicity kept; timeout 4×.
5. **Profile PATCH cannot set a non-ACTIVE home country** (GB COMING_SOON → `INVALID_COUNTRY`): public self-service follows §36 — a market in preparation is not a choice yet. The §14 cross-market guard was therefore verified by flipping the test user's home via SQL (`scripts/p5s3-set-home.ts`), exercising the service guard without weakening the public contract.
6. **Home-country changes never delete data** (§31): moving markets keeps existing goal rows; future edits apply the new market's guards. The explicit "reset personalisation" control stays P5-S5 (this session's profile view already teasers it).
7. **SKIPPED is a first-class end state**: skipping onboarding is a deliberate user choice recorded in the audit trail, never an error — and the flow stays reachable from `#/profile` forever.
