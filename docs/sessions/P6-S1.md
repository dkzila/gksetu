# P6-S1 — CurrentEvent & Source Aggregation

**Master Plan §43, Phase 6 Session 1** · "Implement `CurrentEvent` and source aggregation workflow."
*(Opens Phase 6 — the event-centric current-affairs foundation: the CurrentEvent record, its §12 lifecycle, the source aggregation workflow on the shared §24 evidence registry, and the canonical KnowledgeUnit links. Publishing/revisions (P6-S2), entity/taxonomy linking (P6-S3), the exam-aware feed (P6-S4) and freshness rules (P6-S5) extend this module additively.)*

## Goal

**`CurrentEvent` is live as the platform's first event-centric record** (§12: "event-centric, not article-centric" — one real-world event = one row, whatever the number of publishers covering it), with the **full §12 steps 1–3 + 6–7 editorial workflow**: create the event (with initial source aggregation in the same call — the breaking-news flow before five publishers become five unrelated objects), aggregate evidence from the shared Source registry (URL-deduped, verification states intact, UNRELIABLE never attachable to new events), link the relevant **VERIFIED** canonical KnowledgeUnits (the §7 one-truth rule — the exam layer keeps flowing through the same units), and mature the lifecycle **emerging → developing → stable → archived** with honest reopens and full audit history (§36 — ARCHIVED is read-only; every mutation audited).

## Key Decisions

1. **Events are canonical records, like KnowledgeUnits** (§12/§18): `current-affairs:manage` = ADMIN + COUNTRY_ADMIN only — the knowledge:manage precedent. Writers enter the current-affairs flow at the P6-S2 representation layer (content:manage on event-linked items), exactly as writers create ContentItems but not KnowledgeUnits.
2. **One evidence registry, many objects** (§11/§24): aggregation reuses the shared Source registry by normalized URL — attaching an already-registered URL reuses the record AND its verification state; the response reports which path was taken (`sourceCreated`/`sourceReused`) so editors see the dedup working. UNRELIABLE records cannot be newly attached (the P2-S3 trust rule, now enforced on both the by-id and by-URL paths) — the seeded UNRELIABLE link on the Chandrayaan event stays as preserved provenance history.
3. **The lifecycle is permissive but honest** (§12 step 6): forward progression allows skipping (EMERGING→STABLE when the picture is clear), reopen edges exist in both directions (DEVELOPING→EMERGING, STABLE→DEVELOPING, ARCHIVED→DEVELOPING/STABLE), and every move is audited with the optional reason. P6-S5's automated freshness rules will drive the → ARCHIVED direction on top of this manual machine — no transition vocabulary change needed (target-state form, not action form).
4. **ARCHIVED = read-only, reopen is the only way forward** (§36): edits, attaches and links all 409 on archived events; the reopen transition restores editability. No soft-delete, no hard-delete — fixtures from test runs stay as honest archived tombstones (like the P5 test users).
5. **§7 one-truth link is VERIFIED-gated**: events link only VERIFIED units — DRAFT/IN_REVIEW knowledge is not yet canonical truth. The Chandrayaan-3 event pointing at the Chandrayaan-3 unit (instead of re-entering facts) is the seed's structural proof: the exam layer (§8 mappings) keeps flowing through the SAME unit the event links.
6. **§16 slugs: explicit = identity, generated = suffixed**: an explicit slug clash is a 409 (never a silent suffix); a title-derived slug gets deterministic `-2`/`-3` suffixes. Both paths enforce kebab-case — the router never concatenates arbitrary input.
7. **Scope/slug immutability over patchability**: §14 scope and country are create-time identity — a mis-scoped event is archived and recreated, keeping the audit trail honest (the KU/taxonomy precedent).
8. **The `entities` field of §6 is deferred, not faked**: no JSON placeholder — the Entity model + event-entity links land in P6-S3 as the schema's documented extension point.
