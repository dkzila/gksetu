# P8-S2 — Notifications Engine and Preferences

**Master Plan §43, Phase 8 Session 2** · "Implement notifications engine and preferences."
*(The §27 expanded contract: channel-agnostic triggers — email, web-push, mobile-push, the last modeled now and delivered once the app exists; the four reader trigger moments — current-affairs coverage going live on followed exams/topics, new Knowledge Units verified into followed exams' syllabus coverage, spaced-review revision digests, corrections published to saved items — plus the editorial trio — task assigned, review requested, feedback report received (modeled, wired at P8-S3); every NotificationEvent referencing its triggering object, target user, channel and queued/sent/failed/read status; per-category × per-channel NotificationPreferences — never all-or-nothing; and the §27 philosophy riding §9: every notification EXPLAINABLE — "You're getting this because you follow [Topic]" — with a one-tap mute for the specific follow that caused it.)*

## Goal

**Every notification is explainable, controllable and honest about its delivery.** The engine fans each trigger out per enabled channel (one `NotificationEvent` row per channel, batched by a per-notification `batchId` — the in-app surface reads and marks whole notifications). Trigger matching reuses the exact predicates the combination engine and exam-aware feed apply (`windowContains` + `mappingInEffect` + §14 unit-visibility), so notification matching can never drift from queue matching. The context is an §36-honest snapshot at trigger time (like a share card): title, the complete §27 reason sentence, the matched follows with their one-tap-mute removal requests, the §16 canonical path (market-resolved per §14 — country-scoped objects in their own market, GLOBAL objects in the recipient's home market) or the private in-app path (`#/dashboard`, `#/console`). The lifecycle is §27-exact — QUEUED at fan-out, SENT/FAILED through a transport on dispatch, READ in-app (batch-level: seen is seen, and a row read before dispatch never delivers) — with MOBILE_PUSH honestly held QUEUED (no transport exists until the app, §39). Delivery in this build is the modeled dev transport (server-log record, honestly labeled; the swap point for real email/web-push infrastructure). Serving the notification center IS per-user delivery (lazy revision-digest ensure + opportunistic dispatch — the §22 lazy-materialisation precedent), with an audited ADMIN dispatch sweep for batch operations. Preferences are sparse (no row = stated defaults: email + web push on because §10's follow contract includes notifications, mobile push off because it cannot deliver) and one channel × category per PUT — one coherent audited operation.

## Key Decisions

1. **One row per channel, batched by batchId** (§6/§27): the schema mandates channel on the event row; batchId groups the channel rows of one notification instance so the in-app surface reads and marks WHOLE notifications (READ is batch-level) — a row read before dispatch never delivers ("seen is seen", the pull-model honesty).
2. **Trigger matching reuses the engine's predicates** (§11/§8/§12): `windowContains` + `mappingInEffect` + ACTIVE-exam + §14 unit-visibility — imported from the exams-syllabus/exam-mapping modules, never re-implemented, so notification matching cannot drift from queue matching. The CA trigger fires on the FIRST published representation only (the P6-S2 page gate — a second language publishing later is not the moment); scheduled materialization fires it too (the same goes-live moment).
3. **Saves are the correction audience, stated honestly** (§27/§31): "previously read" is not a tracked per-user signal on this platform (reading is not recorded — §31 minimisation), so savers are the honest audience and the doc + reason sentence say exactly that.
4. **Sparse preferences with stated defaults** (§27/§10/§39): no row = email + web push ON (following IS the opt-in — §10 names notifications in the follow contract) and mobile push OFF (a channel that cannot deliver defaults off); an explicit row either way is the honest stored choice, one PUT per operation (the collection-PATCH audit-coherence precedent).
5. **The modeled dev transport, honestly labeled** (§27/§29/§39): EMAIL/WEB_PUSH dispatch through a transport that records the delivery in the server log — never pretending an email left the building; MOBILE_PUSH has no transport entry at all, so those rows stay QUEUED (held for the app — nothing failed); opening the center dispatches your own queue (pull-model delivery), the ADMIN sweep does it platform-wide (audited with counts, the freshness-sweep precedent).
6. **Best-effort wiring, one-way module boundary** (§28): the knowledge/content and editorial services call the notify functions after their own audited mutations, wrapped so a notification failure never fails the publish; audience reads query UserFollow/SavedItem rows directly (the sharing module's read-only projection precedent).
7. **The FEEDBACK_REPORT_RECEIVED trigger is modeled, not wired** (§27/P8-S3): the enum value exists per the §27 contract and the console states it lands with the public feedback loop — no row is ever created for it yet.
