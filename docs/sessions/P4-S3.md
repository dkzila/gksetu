## Key Decisions

1. **The coverage read is reused, never re-implemented, for the exam page** — the header comes from the public exam detail, the tree from the requirement layer's public coverage read: identical §8/§36 semantics by construction. Only the study list's strongest-row rollup and ranking are new logic (the §11 engine's base order, mirrored and documented in-Comparator).
2. **The syllabus page composes from the FULL node tree, not the pruned coverage tree** — mapping-bearing pruning would hide mapping-free syllabus sections; a syllabus topic is part of the exam even before units map to it (the seed's `constitutional-framework`-on-UPSC two-placement/zero-unit case renders honestly). Mapping visibility re-applies the requirement layer's exact public rules.
3. **The syllabus-topic page is CURRENT-only by design** — it is an SEO surface answering "today"; §36 history stays on the exam page's explicit `?version=` read (one historical affordance, consistently placed).
4. **One exam-card composition** (`composeExamCards` in composition-helpers): the §34 homepage directory and the exam page's §33 related links share §8 liveness, §36 CURRENT-version resolution and §37 ordering — P4-S2's homepage behaviour is unchanged (regression-verified).
5. **Cross-exam counts are always today's signal** — on a historical window read, a study card's "N exams need this" chip reflects today's CURRENT versions while its §8 row carries the historical window's own vocabulary and effective period; both are labelled by their sections, never conflated.
6. **`?version=` is addressable state** like the topic page's `?page=` — the hash is the single source of navigation truth (§16 grammar + §36 window), the back button walks window switches, and every exam switch starts at the current version.
7. **Optional `onOpenExam` on the reader** — the §22 knowledge page's exam-coverage panel gains in-app navigation only where the callback is provided (the product surface); the console verification surface keeps its exact P2-S5/P3-S5 behaviour.
