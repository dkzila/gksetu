# P7-S4 — Mastery Tracking and the Revision Queue

**Master Plan §43, Phase 7 Session 4** · "Implement mastery tracking and revision queue."
*(The §6 `MasteryState` row — "Per-user, per-Knowledge-Unit/topic proficiency: user_id, knowledge_unit_id, mastery_score, last_reviewed_at, next_review_at" — derived exclusively from submitted `TestAttempt` history (§22: "Mastery state per Knowledge Unit/topic, derived from TestAttempt history"), scheduled by §22 spaced review (perfect rounds at 1 → 3 → 7 → 14 → 30 → 60 days; any wrong or unanswered answer resets the streak and schedules tomorrow), surfaced as the dashboard's due-revision queue (§22: "what matters now — combined-exam queue, due revisions"), folded into the §11 step 7 queue ranking ("user state (mastery, revision due-date)" — the REVISION_DUE tier), and treated honestly as a §9 implicit signal: explainable reasons on every row, listed on the §31 controls surface, cleared by the explicit reset while the immutable §6 attempts survive. Combined-exam assessment scope is deliberately NOT here — P7-S5.)*

## Goal

**Every submitted mock test builds a per-unit spaced-review schedule, and the learner's surfaces rank and render it.** The `MasteryState` row (§6) is per user × canonical unit — the Topic/Source/Entity "reference record" discipline applied to user state: one row whatever the number of attempts touching the unit, updated by exactly one write path. `submitAttempt` folds every unit a submitted attempt touched into the user's rows INSIDE the attempt's claim transaction (§6 immutability makes the fold naturally exactly-once: an attempt can transition IN_PROGRESS → SUBMITTED exactly once, and the fold rides that same conditional claim — never applied twice, never lost to a crash between claim and fold). `mastery_score` is plain overall accuracy (correctCount/attemptedCount) — §9 "explainable", never a proprietary black box; `streak` counts consecutive perfect rounds and drives the §22 scheduler. The revision queue (GET /api/mastery + the dashboard's "Revision queue" section) ranks by overdue-ness then lowest score, exposes the 7-day horizon and the §22 "weak topics" list, states its scheduling rules verbatim (§9 transparency), and links every row back to the §16 knowledge page — §22's "revise loops back to learn". On the dashboard the queue's tier system gains `REVISION_DUE` above goal subjects (§11 step 7's user-state input — a due review is what matters NOW), queue rows carry mastery chips, and the knowledge page gains the "Your mastery" strip beside the QnA/practice layers (the §22 learn → practice → revise flow on one page). The §31 reset clears the derived rows (an implicit §9 signal) while attempts survive like saves; the inventory (§9) lists the implicit layer with its effects and the honest provenance note.

## Key Decisions

1. **One write path, exactly once** (§6/§22): mastery folds ONLY inside submitAttempt's claim transaction — the conditional IN_PROGRESS → SUBMITTED update makes the fold naturally idempotent; no route, sweep or admin path writes MasteryState.
2. **Plain accuracy + streak, stated rules** (§9): masteryScore = correctCount/attemptedCount (explainable, no black box); the interval ladder and slip-reset ship verbatim in the API (`scheduling.rules`) and render on demand — the §9 transparency contract applied to implicit signals.
3. **REVISION_DUE outranks goal subjects** (§11 step 7/§22): a due spaced review is time-sensitive "what matters now" — the tier order is REVISION_DUE → GOAL_SUBJECT → FOLLOWED_SUBJECT → EXAM_SCOPE; untracked units keep the engine's base order.
4. **Derived clears, history survives** (§31): the reset removes MasteryState rows (the implicit signal) but keeps attempts (immutable §6 history, like saves §10); new attempts rebuild mastery from that point — the receipt and audit say exactly that.
5. **Topic mastery is computed, never stored** (§46.3): the §22 "per Knowledge Unit/topic" topic layer is a request-time rollup of unit states — one §6 row shape, no stored duplicate.
6. **The seed replays the live rules** (§45): fixtures fold through the exported `computeMasteryTransition` over the user's full attempt history (chronological), rows created only when missing — never a second scheduler, never overwriting live state (§36).
