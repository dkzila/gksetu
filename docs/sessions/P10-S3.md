## The Evaluation

### Caching — justified, delivered, inventoried

The §29 cache trigger is "repeated expensive reads" — P10-S1 measured exactly those and the justified caches are now live. The complete ledger (all in-memory, all read-path-only, all epoch-guarded for the per-route-bundle dev reality):

| Cache | TTL | Guards the measured cost | Delivered |
|---|---|---|---|
| Locale snapshot (`country-locale/cache.ts`, P9-S2) | 60s | Country/language config reads on EVERY request (the pooler RTT × every surface) | P1-era pattern, P9-S2 hardened (globalThis + epoch) |
| Taxonomy tree (`taxonomy/cache.ts`) | 60s-class | The public tree walk per homepage/topic page | P1-S4 era |
| **The census cache** (`sitemap-service`, P10-S1) | 60s, single-flight | The ~14-query census walk × /sitemap.xml, segments, seo status, market-ops ×2 | **P10-S1** — sitemap 3,593→7ms, summaries 4,250→769ms |

What is deliberately NOT cached: every content read (the §36 live-revision guarantee — a fresh publish must serve immediately), the observation import guard (a census guard reads the freshest truth), the personalisation reads (§9's per-user freshness), the audit trail. **No external cache infrastructure (Redis &c.)**: the working set is small, the hit patterns are per-process, and the in-memory TTL form has no additional failure mode (§47 — a smaller system whose behaviour everyone can reason about).

### Queues — not justified at the measured load

The §29 queue trigger is "long-running/async workloads". The candidates, measured:

1. **Notification fan-out** (the §27 engine): batched in-request, ~1 NotificationEvent row per enabled channel per event — milliseconds at dev scale. The modeled dev transport makes dispatch observable without a broker. A queue becomes justified when fan-out per trigger grows into bulk email/push territory (the §39 app era).
2. **The launch/pause reindex** (P9-S2): synchronous in-request, seconds at 49 documents, failures reported in the response (never thrown). A job queue becomes justified when the rebuild takes request-scale-unfriendly time (the re-evaluation trigger: reindex > ~5s on a colocated DB).
3. **AI suggestion jobs** (§26): the translation assist is a synchronous model call with a hard request budget (§37 honest errors, no partial state). Classification/mapping/dedup assists (P10-S4) stay synchronous for the same reason — a suggestion the operator waits ~seconds for is a better contract than a job they must poll (§9: explainable beats asynchronous at this scale).

### Async processing — not justified

Every measured slow path (P10-S1) is either now cached (the census family), bounded by the DB RTT (the composition chains — a batching problem, not an async problem), or already reported-not-thrown (the reindex). No workload exists that needs background processing the request/response contract cannot honestly carry.
