# P8-S1 — Sharing and Share Metadata

**Master Plan §43, Phase 8 Session 1** · "Implement sharing and share metadata."
*(The §21 sharing system: a share action on every shareable canonical page — knowledge page, current-affairs item, topic, exam, practice question, eligible collection; stable share URLs that ARE the §16 canonical paths, parsed and REBUILT canonically server-side so a shared link never depends on how the sharer reached the page; share cards identifying the content title, the topic and the platform branding (never the sharer's identity); the Web Share API where available with a copy-link fallback; private collections exposed ONLY when the owner explicitly opts in (visibility PRIVATE ↔ LINK, one audited operation per patch); private user data never in public share metadata — the public shared-collection payload carries public content titles, honest §36 statuses and §16 paths, nothing else; and share events tracked as analytics events (§32's Sharing family: share actions + landing visits), never as a substitute for real social-network analytics.)*

## Goal

**Every shareable canonical page carries a share action, and every shared link is stable, canonical and honest.** The share URL is the §16 canonical path resolved against the origin (`origin/#<canonicalPath>`) — the same grammar the hash router mirrors, so a mobile client (§39) shares the exact string the web app renders. The share dialog previews the §21 card (title + topic + branding trio) served by `GET /api/share/metadata?path=…`: the server parses the path (the router grammar, market prefix included), resolves the object behind it (existence + the same public gates the save module applies — §36 honesty: VERIFIED/OUTDATED units, published-coverage events, ACTIVE/RETIRED exams/topics, PUBLISHED questions), corrects the market for country-scoped objects (§14 — a GB exam's canonical link lives in the UK market whatever the sharer's market), and REBUILDS the canonical path from the object's own identity — never echoing input. Questions share as their unit page + the addressable `?q={id}` focus (a new router param that scrolls to and highlights the card). Collections gain the §21 eligibility mechanism: `CollectionVisibility.LINK` — the owner's explicit opt-in via `PATCH /api/collections/{id} {visibility}` (audited `user.collection.share`, available for the default "Saved" bucket too: sharing is the owner's choice over their own bucket), an unlisted noindex landing view at `#/collections/{id}/` (public items only, no owner identity), and one-click revoke. Both share actions (Web Share / copy-link) and page-load landings on shareable surfaces record §32 share events — anonymous-friendly (identity only when a token rode the request; landings never), object-guarded first (no dead links, no private leaks), kept by the §31 reset (analytics history, like attempts) and listed honestly on the controls surface.

## Key Decisions

1. **The share URL is the §16 canonical path, rebuilt server-side** (§16/§21): the client passes the path it is on; the server parses the router grammar, resolves the object, corrects the market for country-scoped objects (§14), and REBUILDS the path from the object's own identity — the copied link never depends on how the sharer reached the page, and non-canonical input (`/in/…`) normalizes away.
2. **Eligibility mirrors the save gates** (§36): the same public statuses make an object shareable (VERIFIED/OUTDATED units, published-coverage events, PUBLISHED questions, ACTIVE/RETIRED exams/topics) — a shared link always opens a real page; the honest reasons ship verbatim.
3. **LINK, not PUBLIC** (§21): a shared collection is unlisted — reachable only via the stable link, never listed or indexed (noindex), revocable in one click; the response to a private/unknown id is a typed 404 that reveals nothing.
4. **One visibility write path, one audited operation per patch** (§28/§30): `setCollectionVisibility` is the only writer; the PATCH schema enforces exactly one of name|visibility so each audit row is one coherent action. Sharing is available for the default bucket too — the §10 immutability rules protect name/deletion, not the owner's visibility choice.
5. **Anonymous-friendly analytics, guarded first** (§21/§31/§32): share events attach identity only when a token rode the request (landings never); the object resolves and passes the public gates BEFORE the row is written (no dead links, no private leaks); the receipt leaks no counts; the §31 reset keeps them (activity history, like attempts) and the inventory says exactly that.
6. **A landing is a page LOAD, honestly defined** (§36): the beacon fires once per load when the app STARTS on a shareable surface (the mount-time hash must still be live) — in-app navigation never counts; the definition is stated in the code and this doc.
