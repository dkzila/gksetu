## Goal

**An event's language-specific explanations are ContentItems** (§12 step 4 — "create language-specific ContentItems for explanation"), riding the SAME §19 workflow as unit representations (DRAFT → IN_REVIEW → SCHEDULED/PUBLISHED, writers author via `content:manage`, editors publish via `content:publish` §18), the SAME §36 revision machinery (immutable published snapshots, corrections carry change summaries — never silent edits) and the SAME §24 provenance (item-level evidence links on the shared Source registry). The **public §16 event page** assembles what a reader needs (§22-style): the canonical record (what happened / when / where / why it matters), the published representations in the resolved language (live revisions only), the §12 step 2 aggregated evidence with verification states, the §12 step 3 canonical KnowledgeUnit links (the §7 one-truth rule), the §35 translation surface — with an honest canonical-fallback presentation when the resolved language has no published update yet. Events become **searchable** (§17: `CURRENT_EVENT` documents with eventDate freshness and §8 exam relevance flowing through the linked units) and **discoverable** (§34 homepage current-affairs list + sitemap `current-affairs` segment).

## Key Decisions

1. **Event representations ARE ContentItems with an event anchor** (§12 step 4 verbatim). The anchor is an XOR (`unit` | `event`, never both, never neither) — one canonical record per representation, generalising §7's "representation of a canonical record". This reuses the entire §19 workflow, §36 revision machinery, §24 provenance and the editorial workspace instead of duplicating any of it.
2. **DB uniqueness covers unit anchors; the service covers event anchors.** Postgres treats NULLs as distinct in unique indexes, so `@@unique([knowledgeUnitId, languageId, format])` keeps fully protecting unit items while event items (NULL unit id) get the same `REPRESENTATION_EXISTS` 409 from an explicit service check — documented in the schema, verified by the suite.
3. **The anchor publish gate** (§7/§36): VERIFIED unit or non-ARCHIVED event. EMERGING events publish — breaking news is the point (§12); ARCHIVED is read-only end-to-end (no creates, no publishes, no schedules — reopen first), exactly like archived units.
4. **Freshness = the event's own date** (§17.7): current affairs are fresh by when they HAPPENED, not by when a correction landed — a correction to a two-month-old story doesn't make it breaking news again. The query service's 30-day window applies uniformly.
5. **Publication is the public gate** (§19/§35): an event without a published representation in a country-configured language has no public page — a clean 404, exactly like the EMERGING state before the first publish. ARCHIVED events keep their pages as permanent historical reference (§36 stable identity). Canonical fallback (record + evidence + units, no representations) is the honest §35 answer for a language without coverage — never a machine-translated placeholder.
6. **§8 exam relevance flows through the §7 links**: event documents carry `examRefs` from their linked units' in-effect mappings — the exam layer never re-maps events directly; the one-truth rule holds in search too (search results show "In the current MP Police Constable syllabus" via the linked Chandrayaan unit).
7. **Writers read the event directory** (content:manage) but never mutate events (current-affairs:manage) — the "see the board, work your scope" §20 parity; the §18 gate is unchanged (writers submit, editors publish — proven on an event representation).
8. **Two pre-existing gaps closed in passing**: source-link management now enforces the §20 writer language scope (it previously skipped the language narrowing), and the admin content list gained the missing SCHEDULED status filter — both content-service parity, both suite-covered.
