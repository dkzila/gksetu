# P6-S3 — Current-Affairs Taxonomy/Entity Linking

**Master Plan §43, Phase 6 Session 3** · "Implement current-affairs taxonomy/entity linking."
*(Completes §12 step 3's richer layer: the `Entity` reference registry — persons/places/organisations/concepts as canonical records with aliases and §14 scope — event-entity links ("who/what this event is about"), additional-topic cross-filings beyond the required primary, ENTITY joins the §10 follow vocabulary, and entity names/aliases become first-class §17 search terms. ## Goal

**Events link canonical entities and cross-file under additional topics** (§12 step 3 — "attach entities, countries, topics and relevant KnowledgeUnits"). The `Entity` model (§6 row: "Person/place/org/concept etc. — id, type, canonical name, aliases, country") follows the Topic/Source canonical-reference precedent: **one row per real-world entity, whatever the number of events that mention it** — never content, never a duplicate per story. §14 scoping mirrors Topics exactly (GLOBAL = world reference, ADMIN-managed; COUNTRY = one market); linking is deliberately NOT scope-checked (a GLOBAL event may link a COUNTRY entity and vice versa — links are editorial metadata governed by the event's manage permission, the §24 shared-registry philosophy). §36 soft delete throughout: RETIRED entities stop new links/follows, existing links stay as honest history. Entity names + aliases enrich the §17 search surface (alias "ISRO" finds the Chandrayaan landing), the public §16 event page renders entity chips and cross-filing links, and ENTITY joins the §10 follow vocabulary with an honest no-page-yet summary (`canonicalPath: null`) and a `FOLLOWED_ENTITY` signal in the §9/§31 personalisation inventory.

## Key Decisions

1. **Entities are canonical REFERENCE records, never content** — the Topic/Source precedent. One row per real-world entity; events link it via link rows; detach never deletes the registry record (§36). Five publishers covering the ISRO story share ONE ISRO entity.
2. **§14 scoping on the registry, NOT on the links.** GLOBAL entities are ADMIN-managed world references; COUNTRY entities belong to one market. But linking is editorial metadata on the EVENT — a GLOBAL event may link a COUNTRY entity (the G20/IN event links New Delhi) and vice versa, governed by the event's manage permission. The §24 shared-registry philosophy applied to reference data.
3. **Cross-filings extend §13 without demoting the primary.** The event's required `topicId` stays the breadcrumb anchor; `CurrentEventTopic` rows are additional filings for stories that belong under several branches (Chandrayaan → ISRO Programmes AND Space Technology AND Science & Technology). §13/§14 containment is enforced at attach: a COUNTRY topic files only a same-market COUNTRY event.
4. **ENTITY follows are signals, not retrieval surfaces (§10).** Entities carry no §16 page in v1 — the summary returns `canonicalPath: null` (the honest §37 answer) and the feed surface is the events tagged with the entity. RETIRED entities stop new follows; existing ones stay listed with their state (§36 honesty, mirrored in the inventory effect sentences).
5. **Search enrichment rides the event documents** (§17): entity canonical names + aliases and additional-topic names/aliases join `neutralText` and the alias set at index time — no separate entity document type, no query-path changes; the alias "ISRO" finds events whose titles never say ISRO. RETIRED entities still index: their links are honest history.
6. **The registry permission and the link permission are deliberately different**: `entities:manage` (ADMIN/COUNTRY_ADMIN, the taxonomy precedent) governs the registry; event links ride `current-affairs:manage` on the event — a market's current-affairs editor links entities without owning the registry.
7. **Slug immutability + type/scope immutability (§36)**: a mis-typed or mis-scoped entity is retired and recreated, never silently reclassified — the audit trail stays honest. The §16 kebab-case slug is reserved now for future public entity pages.
