## Goal

**The §32 product half as one honest aggregate read.** The six product families — Discovery, Relevance, Learning, Retention, Content, Sharing — computed from the stores the producing modules already write (§28: this module owns no data; it only reads). Every metric carries its derivation (§9 explainability — "9 successful of 15 queries" style, so a number is never a mystery); every family states its honest gaps (what is deliberately not measured, why, and when it lands); the §32 headline and the pageview warning ride every response. Exactly ONE new instrumentation was needed: `SearchQueryLog` — deliberately **anonymous-only** (no userId column exists at all — a stronger §31 stance than ShareEvent's optional attribution: a failed search says nothing about who failed, and a search can never become a profile). There is no pageview counter anywhere by design — every metric is an intent-bearing action (a query typed, an exam followed, an attempt submitted, a report filed, a link shared).

## Key Decisions

1. **Anonymous-only search logging — a stronger §31 stance than ShareEvent** (§31/§17): ShareEvent attributes when a token rides the request; SearchQueryLog has **no userId column at all**. Search is a per-QUERY surface (§17 explains every match on its own merits) — attribution would build a search profile, which §31's "collect only signals needed" forbids. A failed search says nothing about who failed; that is the point. The §31 reset never needs to touch the store, and the §9 inventory says so ("nothing to reset").
2. **No pageview counter, anywhere** (§32's headline rule): every metric is an intent-bearing action. Topic-hub visits, referrer-based organic attribution and session instrumentation are stated as honest gaps with their landing points (P8-S5 / deliberately-not-built) — never silently omitted.
3. **The module owns no data** (§28): SearchQueryLog belongs to the search module (the producing surface owns its event store — the ShareEvent precedent); the analytics module is a read-only aggregator. Every read is AGGREGATE (count/groupBy/distinct) — §31: no per-user row ever crosses the analytics boundary.
4. **ADMIN-only platform surface** (§38): search, learning, retention and sharing are cross-market by nature; attempts carry no country, so a per-country split would be a partial cut some stores cannot honestly support. The 403 states the scope reason; the feedback queue keeps its §38 workspace split (the P8-S3 read over the same store is the §38-scoped view, stated in the volume derivation).
5. **The console's own demo queries log honestly** (§37 client-agnostic): the P4-S1 console section's auto-demo search is a §17 query like any other — the log records what happened; intent-filtering is how analytics lies start. The HTTP E2E resets the store before asserting exact counts, so both layers stay deterministic.
6. **Windows: flow vs stock, stated in every derivation** (§36-honest): flow metrics (queries, submitted attempts, shares, reports, resolutions, notification reads) honour `?days=`; stock metrics (status distributions, mastery bands, the revision queue) are current state and say so. The time-to-correct window rides `resolvedAt` (§44's resolution moment) — the same per-report pattern the P8-S3 queue stats seed, now platform-wide.
